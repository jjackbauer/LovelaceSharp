## 3. Cost attribution (the answer to the central question)

For a 1M-element boxed elementwise **add** (625 ns/element, 100%):

| Component | Cost | Share |
|---|---|---|
| Real arithmetic + allocation (`NdArray<Real>` = 535 ns) | 535 ns | **86%** |
| Value boxing + WidenPair + Kind switch + `NumericOps` dispatch | 90 ns | **14%** |
| IField interface + List result + iteration (over double) | 2.8 ns | 0.4% |

For a 1M-element boxed elementwise **multiply** (1190 ns/element):

| Component | Cost | Share |
|---|---|---|
| Real arithmetic + allocation (1080 ns) | 1080 ns | **91%** |
| Value boxing + dispatch | 110 ns | **9%** |

**matmul** slowdown vs `double`: `NdArray<Real>` is ~243× and `NdArray<Value>` ~279× slower than `NdArray<double>` at 100×100, with ~4.1 GB allocated for a single 100×100 product (the accumulation Real per inner iteration). `double` 1000×1000 matmul = 4.0 s; Real would extrapolate to ~16 min.

## 4. What this means for the design (conclusions)

1. **The bottleneck is Real arithmetic + allocation, NOT boxing.** Boxing/dispatch is only ~9–15% of the boxed elementwise cost. The task's hypothesis ('maybe boxing is the real bottleneck') is falsified by measurement — the real bottleneck is the arbitrary-precision Real scalar path (add ~537 ns, mul ~1080 ns per element, with 356 B–1.8 KB allocated per element).

2. **Homogeneous typed arrays recover only ~9–15%** on elementwise arithmetic. That is real and worth having, but it is NOT the headline speedup. Replacing `NdArray<Value>` with `DenseArray<Real>` alone will not make elementwise add dramatically faster.

3. **The large numeric-throughput win requires one of:** (a) an optimized low-precision `Real` internal representation (explicitly deferred and out of scope for the array redesign), or (b) **opt-in machine types** (`DenseArray<double>`/SIMD backend) as a specialized backend for hot loops. This is a benchmark-driven conclusion, not a premature 'use double' leap — `Real` stays the default; machine types are the opt-in fast path.

4. **This redesign's clearly-attributable wins are structural, not arithmetic:** views (transpose 26 ms → ~0; slicing stops copying), contiguous buffers, kernel dispatch (blocking/SIMD for the machine backend), and the ~9–15% boxing removal. Plus the dtype/plugin boundary (§5, §8 of the requirements).

5. **Allocation reduction is a high-value target even without changing Real precision.** Kernels that reuse buffers and accumulate in place would cut the 356 B–1.8 KB/element and 4 KB/inner-iter GC pressure substantially, helping both Real and machine backends.

6. **Peak memory today is dominated by the per-element object graph** (Real = Natural limbs + lazily-computed decimal string + Integer + Real wrapper). `DenseArray<Real>` with a packed buffer still stores one `Real` object per element, so it fixes iteration/cache behavior but not the object-per-element memory model — that is a separate `Real` representation question.

## 5. Caveats

- Stopwatch + `GC.GetAllocatedBytesForCurrentThread`, reps 2–20; treat as order-of-magnitude, not BenchmarkDotNet-precision.
- Allocation deltas between `nd-real` and `nd-value` are noisy (the counter is thread-local and reps small); the time-based attribution (86% / 14%) is the reliable signal.
- Operands are 16-significant-digit, non-periodic Reals (the 'low-precision Real' case). Larger digit counts are slower; this baseline is the optimistic end.
- Not yet measured (deferred to a BenchmarkDotNet-grade rerun): scalar broadcast, construction/literal promotion, dtype coercion, and stride slicing (no slice syntax exists yet).
- 10M elementwise is measured only for `double` — 10M `Real`/`Value` elements are memory-prohibitive (hundreds of MB to ~GB).
