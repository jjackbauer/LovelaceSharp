[ecosystem-api.json](ecosystem-api.json) — every member with kind, accessibility, disposition

## 0. What is counted, and how

The scan reads every `.cs` file under each of the 19 production project directories named in
`parity/projects.toml` (test projects, `bin`, `obj`, `docs`, and parity tooling are not product
surface). Comments and string literals are blanked first, so a declaration inside either cannot
enter the inventory. A type is **externally visible** when it is `public` and every enclosing type is
also public; a member is externally visible when it is `public` or `protected` (interface members are
implicitly public). Types and members that are declared public but are unreachable from outside the
assembly are counted as *unreachable public declarations* and excluded from the surface totals.

The scan is a source scan, not reflection: it cannot execute the frozen assemblies here (the
VSTest host is blocked in this environment — see parity/README.md). Its limits are explicit:
explicit interface implementations are private and not listed; attributes are dropped; overloads
are distinguished by their parameter text; nested types are resolved through their enclosing
chain; a declaration the parser cannot classify is counted and quoted in the JSON, never
silently dropped. The ceiling above makes a parser regression a gate failure, not a smaller
number that looks like progress.

## 4. The .NET compatibility decision (ECO-007)

**Decision: no .NET consumer requires continued compatibility through a C ABI, an FFI bridge, or
a C# wrapper. None is built, none is needed, and none is planned.**

Justification, in the order the evidence was checked:

1. **The consumers are process-level.** Every consumer that crosses the .NET boundary in this
   repository spawns a published executable and reads stdout or a file (CON-001, CON-005,
   CON-006, CON-007, CON-009, CON-012). The published surface they depend on is the versioned
   JSON envelope, argv/stdin, the graph JSON, MathIR text, symbolic text and SVG — all
   process/file formats (FMT-001..FMT-009), not managed object layouts.
2. **No interop mechanism exists to preserve.** The generator scans every tracked C# file for
   `DllImport`/`LibraryImport`/`NativeLibrary` and every tracked Rust file and manifest for
   `extern "C"`, `cdylib`, `staticlib` and `no_mangle`: 0 matches (table below). There is no bridge to keep working, and
   a C ABI would be new surface with no consumer.
3. **The only assembly-level consumers migrate together.** The benchmark projects (CON-014) and
   the C# test suites compile against the libraries; they are part of the same solution and are
   retired or replaced with the reference, not hosted by the Rust build.
4. **The desktop is replaced, not embedded.** Lovelace.Studio becomes a native Rust application
   (CON-002); it does not host the .NET engine through FFI. A wrapper would preserve a host
   process the migration is explicitly removing.
5. **Fallback is the reference, not a bridge.** REQ-009 keeps C# as the reference until cutover;
   if an out-of-tree .NET consumer appears, the recorded fallback is to keep the C# solution
   buildable (it is, and CI proves it) rather than invent an ABI. No such consumer is known.

Consequences recorded so the decision is testable: no `cdylib` crate type, no C headers, no
wrapper package, and no `unsafe` FFI block may be added without a new requirement row and user
approval. The scan that proves the absence today:

| Interop mechanism | Files matching |
|---|---:|
| C# P/Invoke or native-library loading (DllImport / LibraryImport / NativeLibrary) | 0 |
| Rust C ABI exports (extern "C" / cdylib / staticlib / no_mangle) | 0 |
